The basics

Do more agents finish sooner?

Not as a rule. More agents help when the job splits into independent pieces, and only until you hit a speed limit.

Think of moving house

24 boxes, one hour each. Friends help, but only so many fit through the door at once. Try it.

Splittable?

Only the independent part speeds up. A step that needs the last answer cannot be shared out.

Capped?

Even in a 1,000-agent run, 16 work at once by default. Extra agents wait in line.

Worth it?

Each agent costs tokens and adds merge work. Gains flatten while the bill keeps rising.

The first rule is Amdahl's law: time = (1 − p) + p ÷ n, where p is the share that can run side by side and n is the workers. If 90% runs in parallel, even endless workers cannot beat 10 times faster.

Good and bad sides

Advantages

  • Better coverage on wide tasks.
  • Cross-checking filters weak findings.
  • The main chat stays clean, because results sit in the script.
  • Runs can resume after a stop.
  • Same feature on the API and three clouds.

Disadvantages

  • Token cost grows fast.
  • The headline result is one vendor test.
  • 1,000 total does not mean 1,000 at once.
  • Poor fit for sequential work or edits that collide.
  • Hundreds of outputs are hard to audit.

Which agents does a job need?

Most workflows use four roles. The task decides how many of each.

Planner

Reads the job, lists the pieces, decides the order. Usually one.

Worker

Does one piece with a small, fresh context. The only role that grows with the work.

Checker

Tries to prove a worker wrong. Add it where errors are costly.

Merger

Combines, ranks and removes duplicates. Usually one.

Starting points from Anthropic's scaling guidance and the Claude Code examples. Adjust after a small trial.

Who decides how many agents?

Both, in layers. You set the outer limits. The lead agent chooses the count inside them.

You decide

  • The job and how big it is, such as "audit these 500 files".
  • A ceiling on agents, agents at once, and spend. The platform caps are 1,000 per run and 16 at once by default.
  • Whether to add checkers and which model the helpers use.
  • Whether to start small. Anthropic advises it.
  • Whether to approve a big run. Claude Code warns above about 25 agents or 1.5M projected tokens.

The lead agent decides

  • How to split the job into pieces.
  • How many helpers to start, within your limits.
  • Which pieces run side by side and which wait.
  • In dynamic workflows it writes this as a script you can read.

Good habit: give a clear job, a ceiling and a budget. Ask for the plan and the agent count first, then approve. I found no documentation on exactly how Claude picks the count, so treat that as default behaviour, not a promise.

How work is handed out

Split

Cut the job by a natural unit: a file, a page, a source, a claim. Pieces must be independent.

Scope

Each worker gets one piece, a short brief, and only the tools it needs.

Structure

Workers answer in a set shape, such as JSON, so the next step can read it.

Merge

A script or merger agent collects the results into one answer.

The plan can live in two places. With subagents, Claude decides turn by turn what to run next and every result enters its memory. With a dynamic workflow, a script holds the plan, the loops and the results, which is why one run can reach hundreds of agents.

Step by step or all at once

Which steps can run together?

If step B needs the answer from step A, B waits. If they do not need each other, run them together.

Ask these in order

  • Does B need A's output? Run them in line.
  • Do both write the same file? Run in line, or give each its own copy.
  • Same task on many items? Fan out, one worker per item.
  • Does a wrong answer cost more than a second look? Add a checker.
  • Unknown number of rounds? Loop, with a stop rule such as two rounds with no progress.

Five shapes

Single agent

work→work→work

Few steps that each need the last. Lowest tokens until the memory fills.

Chain

draft→review→revise

Stages that depend on each other. Time adds up.

Fan out

plan→●●●●→merge

Many independent items. Time is the number of rounds. Tokens match doing them one by one.

Fan out + check

plan→●●●→◆◆◆→merge

For costly errors. Two rounds, and roughly double the work tokens.

Loop to a check

fix→test→fix→test

Rounds are unknown, so tokens grow each round. Set a stop rule.

● is a worker. ◆ is a checker that tries to prove the worker wrong.

Reading it

  • One agent re-reads a growing memory every item, so it costs more and may not fit at all.
  • One fresh agent at a time and the team use the same tokens. The team is just faster.
  • Checking roughly doubles the work step.
  • A cheaper model on the work step is the usual saving. Test it on a few items first.

The ceiling is 1,000 in one run. It guards against runaway loops. It is not a target.

Ways to spend less

  • Try a small slice first. One folder or one narrow question. Watch tokens per agent, then scale.
  • Set a small size. It keeps Claude from planning a bigger run than you need.
  • Match the model to the step. Cheap for simple steps, strong for planning and checking.
  • Share the prompt prefix. Agents with the same setup read each other's cache. It lasts five minutes by default.
  • Batch what can wait. It takes 50% off, but answers come back later.
  • Check what matters. Cross-check high-stakes findings, not everything.
  • Keep memory small. Fresh agents avoid the re-read cost of one long chat.
  • Stop loops. End after rounds that make no progress.
  • Do not cut blindly. In Anthropic's analysis of a browsing test, token use explained 80% of the difference in results.

Where it fits

Code audits

Bug hunts and security reviews across a large repository, one slice per agent.

Migrations

Upgrading a library across hundreds of files, with a check pass at the end.

Fact-checking

Verifying a long report claim by claim, with skeptic agents.

Deep research

Reading many sources in parallel, then writing one answer.

Document review

Contracts, tickets or logs where each item can be read alone.

Skip it for

Small fixes, step-by-step reasoning, and edits that touch the same files.

Which jobs use the most agents?

Jobs that repeat one step across a big set and then check it: a codebase-wide bug sweep, a 500-file migration, research cross-checked across sources, or a plan drafted from several angles.

The count adds up fast. One worker and one checker for each of 500 files is 1,000 agents before the planner and merger, so a run that size needs splitting. Most jobs need far fewer. Anthropic reported that early versions of its research system spawned 50 subagents for simple questions, and it corrected that.

How companies plan

I found no published limit on agents per task. What exists is adoption data and the controls that cap spend.

Adoption

Gartner's 2026 survey: 17% have deployed agents and over 60% plan to within two years. Deloitte: 11% run them in production.

Risk

Gartner predicted in June 2025 that over 40% of agent projects will be cancelled by the end of 2027, over cost, unclear value and weak controls.

Strong cases

Software development, customer service, finance operations and data analysis. Sales and marketing results are mixed.

Cost controls

Admins can switch workflows off, limit which models agents use, and set size guidelines. Anyone can stop a run from the workflow view.

A practical plan: pilot on one splittable job, set a small size, measure tokens per agent on a slice, set checking by risk, and expand only when the cost per finished item holds. On a subscription, runs draw on plan limits. On the API they are billed per token.

Adoption figures come from a secondary summary of Gartner, Deloitte and market research, not checked against the originals. Several are vendor estimates.
